Input & form field

A form field is a labelled control with optional hint and validation message. Fields are how members write brags, name organisations, and prove who they are — clarity and honest validation matter more here than anywhere.

Beta text · textarea · select · group · choice

Anatomy

Every field stacks the same four parts vertically with an 7px gap: label, control, and either a hint or a validation message (never both at once).

Error replaces the hint. A field shows a hint or an error — never stacked. The error inherits the same line position so the form doesn't reflow.

Layout

  • Labels above the control, always — never floating or inline placeholders as labels.
  • One column for a focused task (brag editor). Two columns only for short, related pairs (start / end date).
  • Mark the rarer case. If most fields are required, mark the optional ones; if most are optional, mark the required ones — never both.
  • Group related fields into a card section with its own header and Save, per the Card spec.

Do & don't

Do
A tight one-liner.

Visible label above, helpful hint below.

Don't

Placeholder used as the label — it vanishes on type and fails screen readers.

Content

  • Labels are nouns, sentence case, no colon: "Organisation", not "Organisation:".
  • Hints describe the expectation or format; they don't repeat the label.
  • Errors are specific and kind: "That username is taken" — say what's wrong and, where possible, how to fix it.
  • Placeholders are examples, prefixed with "e.g." where it isn't obvious.

Accessibility

  • Every control has a programmatic <label for> association.
  • Errors use aria-invalid="true" and link the message via aria-describedby.
  • Never rely on red alone — the error always carries an icon and text.
  • Focus ring (2px --teal-500, 3px soft halo) appears on keyboard focus of every control.
  • Minimum control height 40px; choice controls have a ≥18px target with a clickable label.
