# Ts

## No mutable state at module scope under SSR
The SSR process imports a module once and keeps it alive across every render, unlike PHP-FPM which resets per request. A mutable binding at module scope is therefore shared by every visitor, so one user's data can render into another user's page.

ESLint enforces this for `.ts` files via `no-restricted-syntax` on `Program > VariableDeclaration[kind="let"]` in `eslint.config.ts`. That selector cannot see inside a component: `svelte-eslint-parser` does not expose `<script module>` declarations as top-level, so a mutable binding there passes lint and must be caught in review.

Keep request-scoped values inside a component instance or pass them as props. A module-level `const` holding a mutable object or array has the same problem and is equally uncaught.

## Inertia pages live per domain, and entries use the plugin's pages shorthand
Page components are in `resources/ts/pages/{app,admin,public}/`, one directory per domain, because each domain builds its own bundle and globs only its own folder. Not `resources/js/Pages`.

Entries use the `@inertiajs/vite` shorthand, `createInertiaApp({ pages: './pages/<domain>' })`, and deliberately pass no `resolve` or `setup`. Writing a manual `setup` costs three things: the adapter's default hydrate-or-mount handling, the Svelte context it builds, and `withApp` entirely, which is typed `never` whenever `setup` is present.

The Boost-managed `inertia-svelte-development` skill says `resources/js/Pages` and never mentions the shorthand, because it describes stock Inertia rather than this project. It is regenerated by `boost:update`, so corrections belong here, not in the skill. See `.ai/rules/skills.md`.

## Shared component state goes in context, never at module scope
A store any component can push into (toast queue, notification list, open-overlay registry) must be created inside a root component and passed down with setContext/getContext.

Never at module scope. The SSR process imports a module once and keeps it alive across every render, so a module-level store is shared by every visitor: one person's toast can render into another person's page. Context is per-component-tree, so each render gets its own.

ESLint cannot catch this. Its no-restricted-syntax rule only sees `.ts` files, and svelte-eslint-parser does not expose `<script module>` declarations as top-level, so a mutable binding there passes lint. Review is the only guard.

Bits UI has no toast primitive, so the queue is ours and this is where the trap will first appear.

## Form fields take their error as a prop and generate their own id
A field receives its validation message explicitly, `error={$form.errors.username}`. It never reads an Inertia form object from context and looks itself up by name.

Two reasons. A typo in a name-based lookup shows no error and no warning, silently. And shared components stay presentational: coupling the library to Inertia's form shape breaks that rule for the sake of saving one attribute.

The field generates its own id with `$props.id()` (Svelte 5.20+), which stays consistent across SSR and hydration, then wires `label for`, `input id`, `aria-describedby` to whichever of hint or error is showing, and `aria-invalid`. Callers never pass an id.

Hint and error are mutually exclusive per the DS Form spec: type them as a discriminated union so passing both fails to compile.
